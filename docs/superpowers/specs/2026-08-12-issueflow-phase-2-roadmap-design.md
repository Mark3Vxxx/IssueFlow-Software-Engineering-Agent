# IssueFlow 阶段二总体路线图设计规格

## 1. 文档定位

本文只规划 IssueFlow 阶段二，不替代整个项目的三阶段路线图。

- 阶段一：单 Agent 可运行 MVP，已经完成。
- 阶段二：多 Agent、30+ Benchmark 与四种架构对比实验，本文范围。
- 阶段三：展示完善、真实 GitHub PR、中英文材料、视频和完整技术报告，后续单独规划。

阶段二采用“证据优先的纵向迭代”：先建立统一实验接口与最小多 Agent 闭环，再分批扩展 Benchmark，经过小规模校准后运行正式实验。阶段二为阶段三保留人工审批、运行恢复、实验看板和 PR 工作流所需接口，但不提前实现这些功能。

## 2. 已确认的约束

- 周期：4–5 周。
- 投入：每周 20 小时以上。
- DeepSeek API 总预算：不超过 300 元人民币。
- 编排框架：LangGraph。
- 仓库范围：3–4 个中小型深度学习仓库。
- Benchmark：新建 20 个严格主集样本，另加 10 个以上探索集样本；阶段一现有 5 个样本只作为兼容回归集，不计入这 20 个严格样本，因此阶段二管理的案例记录总数至少为 35 个。
- 正式架构：Direct、Single、Fixed、Dynamic 四种。
- 重复实验：20 个严格样本的四种架构先各运行一次；再按预先固定的规则选出 10 个关键或不稳定样本，每种架构补跑两次，总计约 160 次正式运行。
- 系统环境：Python 3.11+、Apple Silicon Mac、Docker 默认断网。
- LangGraph 依赖范围：`langgraph>=1.2,<2`；阶段二期间只在计划明确的依赖升级任务中改变该范围。
- 功能成功仍由确定性证据判定，Reviewer 不能推翻失败的测试，也不能替代隐藏测试。
- API Key 只能来自宿主机环境变量，不能进入容器、日志、SQLite、JSON、截图或 Git。

## 3. 阶段二目标与非目标

### 3.1 目标

1. 用统一接口在相同 Benchmark、预算和成功标准下运行四种 Agent 架构。
2. 使用 LangGraph 实现固定四角色工作流和动态 Supervisor。
3. 建立跨 3–4 个仓库的 20 个严格主集与 10 个以上探索集。
4. 引入不向 Agent 暴露的隐藏验证，降低只针对公开测试投机修复的风险。
5. 记录角色级轨迹、Token、成本、工具调用、补丁、路由和停止原因。
6. 在 300 元 API 预算内完成约 160 次正式运行，并生成可追溯的四架构对比结果。
7. 保持阶段一 Single Agent、Docker、安全边界、SQLite/JSON 轨迹和 Streamlit 工作台兼容。
8. 延续“边做边学”，为每个里程碑产出面试复盘材料。

### 3.2 非目标

- 不实现任意仓库导入或通用自动修复平台。
- 不自动推送分支、创建 GitHub PR 或执行其他外部写操作。
- 不建设分布式执行器、远程队列、多用户隔离或生产级恢复系统。
- 不在阶段二完成正式实验看板、演示视频或 4–6 页完整技术报告。
- 不用探索集结果提高严格主集成功率。
- 不预设 Dynamic 或其他多 Agent 架构一定优于 Single。
- 不以单次成功、Reviewer 分数或更大预算宣称普适修复能力。

## 4. 总体实施策略

采用证据优先的纵向迭代，而不是先一次性完成全部 Agent 或全部数据集：

1. 在阶段一 5 个样本上建立统一架构接口和 Direct 基线。
2. 实现固定 Planner → Retriever → Coder → Reviewer 工作流。
3. 实现根据共享状态路由的动态 Supervisor。
4. 先新增 5 个严格样本完成四架构小试跑，再扩展到 20 个严格样本。
5. 补充 10 个以上探索样本，但与正式实验结果分开。
6. 校准预算和失败规则，冻结实验配置后运行四组正式实验。
7. 从 SQLite 原始运行记录生成结果表、图表、失败分析和面试材料。

该顺序保证每一周都有可运行、可验证的闭环，也能在跨仓库扩展前发现多 Agent 状态、预算和轨迹设计问题。

## 5. 总体架构

阶段一的 `RunService` 继续作为外层控制器，负责工作区准备、故障复现、Agent 架构执行、独立验证、diff、确定性成功判定和持久化。阶段二新增统一的 `AgentArchitecture` 边界：

```text
RunService
  └─ AgentArchitecture.run(case, workspace, budget, run_context)
       ├─ DirectArchitecture
       ├─ SingleAgentArchitecture
       ├─ FixedMultiAgentArchitecture
       └─ DynamicSupervisorArchitecture
              ↓
     独立公开/隐藏验证 → 确定性判定 → TraceStore / 实验指标
```

四种架构必须返回同一种运行结果，至少包含状态、停止原因、步骤、角色使用量、工具和补丁次数、Token、成本、墙钟时间及最终消息。`RunService` 不根据架构类型改变成功条件。

### 5.1 Direct

Direct 只允许一次模型调用，根据 Issue 和有界代码上下文生成结构化补丁。它不使用交互式工具，也不根据测试结果迭代。系统仍负责安全地应用补丁和独立验证。

### 5.2 Single

Single 复用阶段一实现：一个 Agent 使用 `search`、`read_file`、`apply_patch` 和登记过的 `run_tests`，在统一预算中循环。阶段二的统一接口不得改变其已有功能语义。

### 5.3 Fixed Multi-Agent

固定工作流为：

```text
Planner → Retriever → Coder → Reviewer
                         ↑         │
                         └─ 有限返工 ┘
```

- Planner：输出结构化修复计划、目标文件、验证条件和风险。
- Retriever：检索代码、公开测试、允许的文档和允许的 Git 历史，返回带路径和行号的证据。
- Coder：根据计划和证据生成最小补丁，并运行登记的公开测试。
- Reviewer：检查补丁是否满足 Issue、是否存在无关改动，并返回结构化意见。
- Reviewer 只可触发预算内的有限返工；最终功能成功仍由系统独立验证决定。

### 5.4 Dynamic Supervisor

Dynamic 在每个角色完成后由 Supervisor 读取当前状态和剩余预算，并从 Planner、Retriever、Coder、Reviewer、停止或失败中选择一个动作。一次只选择一个角色。所有路由选择和简要理由写入轨迹。

IssueFlow 在每次路由和节点执行前后检查预算、最大路由次数和终止条件。Supervisor 无权扩大预算、执行未登记工具、跳过独立验证或改变功能成功状态。

## 6. LangGraph 边界与共享状态

LangGraph 只承担阶段二的角色编排：

- 使用 `StateGraph` 描述共享状态和节点。
- Fixed 使用普通边以及 Reviewer 后的有限条件返工。
- Dynamic 使用条件路由选择下一个角色或结束。
- `run_id` 同时作为 LangGraph `thread_id`。
- 使用轻量检查点支持单次运行内的状态观察和调试。
- 阶段二不承诺跨进程恢复；相关接口留给阶段三。

IssueFlow `TraceStore` 是实验指标和审计证据的唯一权威来源。LangGraph 检查点不能成为第二套成功率或成本数据口径。

共享状态至少包含：

- `case_id`
- `issue`
- `plan`
- `evidence`
- `current_diff`
- `public_test_result`
- `review_feedback`
- `budget_usage`
- `role_history`
- `stop_reason`

大段代码、测试日志和完整 diff 存在工作区或 TraceStore；图状态只保存有界摘要和引用。每个累积列表和字符串都有显式数量或长度上限，防止 Token、内存与检查点无限增长。

## 7. Benchmark 设计

### 7.1 数据集组成

| 数据集 | 数量 | 用途 |
| --- | ---: | --- |
| 严格主集 | 新建 20 | 四种架构正式比较 |
| 探索集 | 10+ | 发现真实场景问题，单独报告 |
| 阶段一兼容集 | 现有 5 | 快速回归和开发调试，不计入严格主集 |

目标仓库以 Python 为主，核心代码约 1k–10k 行；许可证允许研究与展示；能够在 Apple Silicon Docker 中稳定运行；不依赖 GPU、私有数据、人工交互或长期在线服务；依赖固定且存在可独立验证的历史修复。

### 7.2 严格主集纳入门槛

每个严格样本必须具备：

1. 仓库 URL 与许可证。
2. 完整 40 位故障 Git revision。
3. 原始 Issue、PR 或修复提交来源。
4. 修复前稳定失败的复现命令。
5. 可向 Agent 开放的公开测试或验证命令。
6. 不向 Agent 暴露的隐藏验证命令或测试。
7. 真实参考补丁。
8. 参考补丁后公开测试和隐藏测试均通过。
9. 在全新工作区连续回放三次且结果一致。
10. 难度、Issue 类型、预算档位和预计修改范围标签。
11. 不需要网络、GPU、人工输入或敏感凭据。

### 7.3 探索集

Issue 描述不完整、环境只能部分复现、依赖较重、缺乏可靠隐藏测试或需要人工判断的样本只能进入探索集。探索集结果不得与严格主集的功能成功率合并。

### 7.4 防止答案泄漏

- Agent 只能看到故障版本、Issue、公开测试和登记的允许信息源。
- 参考补丁和隐藏测试保存在 Agent 工作区之外。
- 默认禁止读取故障 revision 之后的 Git 历史。
- 参考补丁只能由 Benchmark 验证器使用。
- 轨迹记录每个角色实际使用的信息源。
- 样本构建测试必须证明工作区中不存在参考补丁和隐藏测试。

### 7.5 样本建设批次

1. 阶段一现有 5 个样本：只用于统一接口和图编排回归，不计入阶段二严格主集。
2. 新建首批 5 个严格样本：用于四架构校准试跑。
3. 将阶段二新建严格主集扩展到 20 个样本：用于正式实验。
4. 补充 10 个以上探索样本：只作单独分析。

候选样本依次经过来源与许可证筛选、固定故障版本、公开复现、隐藏验证、参考补丁回放、三次干净工作区验证，最后决定进入严格集、探索集或淘汰。被淘汰候选也记录理由。

## 8. 统一预算与实验公平性

正式对比固定以下条件：

- 同一模型、温度、模型接口和模型版本记录方式。
- 同一故障工作区、Issue 和可见信息。
- 同一 Docker 镜像、资源限制与验证器。
- 同一样本使用同一总预算档位，不为特定架构临时放宽。
- 同一确定性功能成功条件。
- 每个正式运行使用新的 Git 工作区。
- 角色级消耗计入架构总预算，Supervisor 和 Reviewer 的调用也计费。

多 Agent 可以把总预算分配给不同角色，但不能突破样本总预算。阶段二在现有 `small`、`medium`、`large` 档位基础上校准跨架构预算；校准结果必须在正式实验前冻结并记录版本。预算仍限制工具调用、补丁次数、墙钟时间、输入 Token、输出 Token 和 API 成本。

## 9. 正式实验

### 9.1 批次与重复规则

1. 先运行 20 个严格样本 × 4 种架构 × 1 次，共 80 次。
2. 在补跑前根据固定规则选择 10 个关键或不稳定样本。
3. 这些样本的每种架构再补两次，共 80 次。
4. 正式实验合计约 160 次。
5. 探索集只做小规模运行并单独报告。

关键样本选择条件在第一轮完成后一次性执行，规则为：四架构结果不一致、出现可确认的模型或基础设施波动、难度为中高，或代表重要 Issue 类型。不能只因为某个架构表现差就单独增加其运行次数。

### 9.2 API 预算分配

| 用途 | 上限 |
| --- | ---: |
| 多 Agent 开发与调试 | 45 元 |
| 5 个样本校准试跑 | 30 元 |
| 第一轮 80 次正式实验 | 105 元 |
| 关键样本补跑 | 80 元 |
| 失败重跑与 Reviewer | 25 元 |
| 安全余量 | 15 元 |

实验运行器维护人民币累计账本。达到分类上限或 300 元总上限后，不再安排新的付费运行，并保留已有证据；只有用户明确调整阶段二预算后才能继续。

### 9.3 指标

主要指标：

- 严格主集功能成功次数/总次数与成功率。
- 隐藏测试通过次数/总次数。
- 单次运行与成功一次的 API 成本。
- 输入/输出 Token。
- 端到端墙钟时间。
- 工具调用数和补丁次数。

过程指标：

- 各角色调用次数、Token、成本和耗时。
- Supervisor 路由次数和角色切换轨迹。
- Reviewer 返工次数。
- 检索证据引用率。
- 停止原因分布。
- 预算利用率。

报告必须同时显示分子和分母，例如 `13/20 (65%)`，不能只给百分比。

### 9.4 失败分类与重跑

主要失败类别为：

- `reproduction_failure`
- `infrastructure_failure`
- `model_protocol_failure`
- `retrieval_failure`
- `patch_application_failure`
- `public_test_failure`
- `hidden_test_failure`
- `budget_exhausted`
- `review_loop_exhausted`

基础设施失败不计为 Agent 功能失败，但必须单独报告。只有 Docker/网络供应商/API 服务等系统级错误满足预先定义的基础设施失败条件时才能重跑；错误运行和重跑都保留，重跑必须引用原运行 ID。模型产生无效协议、错误补丁或提前结束属于 Agent 结果，不能伪装成基础设施失败。

### 9.5 统计口径

阶段二以描述性统计为主：成功次数/总次数、均值、中位数、范围、重复样本波动、成功一次的平均成本，以及各架构相对于 Single 的成功率和成本差异。20 个严格样本不足以支撑强因果或普适性结论。

## 10. 数据流与错误处理

```text
实验配置冻结
→ 创建运行与干净工作区
→ 复现故障
→ 调用选定 AgentArchitecture
→ 公开测试
→ 工作区外执行隐藏验证
→ 生成 diff
→ 确定性判定
→ 附加 Reviewer 结果
→ 写入 TraceStore
→ 更新实验账本与聚合结果
```

每个节点异常都转化为结构化停止原因并写入轨迹。预算、超时、无效 Supervisor 路由、无效角色输出、补丁应用失败和检查点异常都必须到达终态，不能留下永久 `running` 记录。Reviewer 或 LangGraph 检查点失败时，只降级相应附加能力，不改变已经由公开测试、隐藏测试、diff 和预算证明的功能结果。

## 11. 测试策略

1. **单元测试**：状态模型、预算聚合、路由、角色输出解析、隐藏测试隔离、失败分类和成本账本。
2. **图结构测试**：固定节点顺序、Reviewer 返工上限、Dynamic 合法路由、终止和递归上限。
3. **契约测试**：四种架构接受相同输入并返回同一种结果；历史 Single 行为保持兼容。
4. **确定性端到端测试**：使用固定模型动作，真实运行 Git、Docker、LangGraph、公开/隐藏验证、SQLite 与 JSON，不调用付费模型。
5. **Benchmark 验证**：每个严格样本在全新工作区连续回放三次，证明修复前失败、参考补丁后公开与隐藏验证通过。
6. **真实模型校准**：仅在自动测试通过后启动，先用 5 个样本估计成本与失败模式。
7. **全量回归**：阶段一现有 93 项测试和 5 个 Benchmark 必须继续通过；测试数量可增加，不能以删除旧断言维持通过。
8. **凭据检查**：扫描新增 Git diff、SQLite、JSON 和阶段二产物，确认真实 API Key 未落盘。

## 12. 里程碑与时间安排

### 12.1 2A：统一接口与多 Agent（第 1–2 周）

交付统一架构接口、四种架构、LangGraph 状态和路由、角色级指标、预算与有限返工，并在阶段一 5 个案例上完成回归。

验收要求：四种架构由同一 `RunService` 启动；Fixed 顺序正确；Dynamic 路由可追溯；超时、预算、无效路由和节点异常都有终态；Single 保持兼容。

### 12.2 2B：Benchmark 扩展（第 2–3 周）

交付 3–4 个仓库适配、新建 20 个严格样本、10 个以上探索样本、隐藏测试隔离、元数据和三次连续回放工具；阶段一现有 5 个案例继续作为独立兼容回归集。

验收要求：20 个严格样本全部满足纳入门槛；探索集不进入正式成功率；工作区无法读取答案；所有严格样本三次回放稳定。

### 12.3 2C：校准与正式实验（第 4 周）

交付 5 样本校准报告、冻结的实验配置、第一轮 80 次运行、10 个关键样本选择结果、约 80 次补充运行、API 成本账本和重跑记录。

验收要求：不按实验结果临时修改某个架构；每次运行都有配置、轨迹、结果和成本；功能与基础设施失败分开；总 API 成本不超过 300 元；结果可从 SQLite 重建。

### 12.4 2D：总结与阶段验收（第 5 周）

交付四架构对比表、指标图表、典型案例、阶段二中英文说明、面试问答、三分钟讲稿和阶段三输入清单。

验收要求：四架构都完成 20 个严格样本首轮；10 个关键样本完成三次重复；聚合数字都能追溯到运行 ID；报告区分公开测试、隐藏测试和 Reviewer；结论不夸大多 Agent；阶段一回归继续通过。

## 13. 用户参与事项与边做边学

用户需要亲自完成或确认：

- 审核候选仓库许可证和样本来源。
- 手动理解至少 6 个代表性 Bug。
- 为至少 3 个样本解释隐藏测试如何防止投机修复。
- 记录候选样本淘汰原因。
- 校准后批准正式实验放量。
- 每约 20 次运行检查成本、异常率和数据完整性。
- 人工复核至少 10% 的代表性补丁。
- 用自己的话完成每个里程碑的两分钟复述。

每个实现任务结束后回答七个问题：模块解决什么问题；输入、输出和依赖是什么；最重要的设计取舍是什么；如何验证；可能如何失败；面试官如何追问；如何用两分钟复述。

## 14. 阶段二最终成功标准

1. Direct、Single、Fixed、Dynamic 在同一接口、环境、样本预算和成功判定下运行。
2. 阶段二新建的 20 个严格主集样本覆盖 3–4 个仓库，并全部通过来源、隐藏验证、参考补丁和三次稳定回放门槛；阶段一现有 5 个样本不计入这 20 个。
3. 10 个以上探索样本单独记录和报告。
4. 第一轮 80 次正式运行完成，10 个关键样本完成两次补跑，总计约 160 次。
5. 总 DeepSeek API 支出不超过 300 元，且每笔成本可追溯到运行和角色。
6. 每个正式运行都能从 SQLite/JSON 恢复架构、角色、预算、路由、工具、补丁、公开/隐藏验证和停止原因。
7. 聚合结果可由脚本从原始数据重建，无需手工修改数字。
8. 阶段一回归保持通过，最新真实 `historical-01` 成功证据更新到阶段一评估记录。
9. 阶段二报告明确局限，不宣称多 Agent 普遍优于 Single，也不以 Reviewer 替代功能证据。

## 15. 进入阶段三的接口

阶段二结束时保留以下扩展点：稳定的架构标识、运行配置快照、角色级轨迹、LangGraph `thread_id`、可引用的运行产物和外部操作审批接口。阶段三可以在此基础上实现案例工作台升级、实验看板、人工确认后的分支与 PR、运行恢复、视频和正式技术报告，而无需改变阶段二原始实验数据。
